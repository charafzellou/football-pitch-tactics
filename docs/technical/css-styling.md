# CSS Styling System

The app uses **Tailwind CSS v4** configured via the CSS-first `@theme` approach — no `tailwind.config.js`. All theming lives in `frontend/app/assets/css/main.css`, and every colour in the app is derived at runtime from **two seed ramps** that the player can edit.

---

## The theming chain

This is the core of the system. Nuxt UI 3 resolves every component colour through a chain of CSS custom properties (verified against `@nuxt/ui/dist/runtime/plugins/colors.js` and `@nuxt/ui/.nuxt/ui.css`):

```
--color-brand-{50..950}          ← declared in main.css @theme static
  → --ui-color-primary-{shade}   ← generated by Nuxt UI from app.config ui.colors.primary: 'brand'
    → --color-primary-{shade}    ← Tailwind alias; drives bg-primary, text-primary, ring-primary…
```

The same applies to `--color-shell-*` → `neutral`. Two consequences:

1. **Runtime theming needs no rebuild.** Writing `--color-brand-500` as an *inline style on `<html>`* outranks the `:root` rule Nuxt UI emits, so every `UButton`, `UBadge`, `UInput` and Tailwind colour utility re-colours instantly.
2. **`--ui-radius` alone carries the retro skin.** It drives `--radius-xs` through `--radius-3xl`, so `0.5rem` → `0.125rem` squares off every corner in the app at once.

`app.config.ts` therefore points at our own ramps rather than stock Tailwind palettes:

```ts
ui: { colors: { primary: 'brand', neutral: 'shell' } }
```

## File structure

```
main.css
├── @import "tailwindcss"           ← Tailwind v4 base + utilities
├── @import "@nuxt/ui"              ← Nuxt UI component styles
├── @theme static { ... }           ← brand/shell ramps + animation tokens
├── @keyframes { ... }              ← 15 animation definitions
├── @layer base { :root { ... } }   ← every --app-* token, DERIVED from the ramps
├── @layer base { body, :focus-visible, scrollbars, reduced-motion }
└── @layer components { ... }       ← named CSS component classes
```

## Primitives vs derived tokens

Only a small set of **primitives** is written from JavaScript (`app/utils/themes.ts` → `resolveThemeTokens()`):

| Primitive | Count | Purpose |
|---|---|---|
| `--color-brand-{50..950}` | 11 | Accent ramp → Nuxt UI `primary` |
| `--color-shell-{50..950}` | 11 | Neutral ramp → Nuxt UI `neutral` |
| `--app-seed-pitch`, `--app-seed-gold` | 2 | Single-colour seeds |
| `--app-pos-{gk,df,mf,fw}` | 4 | Position badge colours |
| chrome (`--ui-radius`, `--app-border-width`, `--app-noise-opacity`, `--app-glass-blur`, `--app-shadow-strength`, `--app-kicker-tracking`, `--app-pitch-stripe`) | 7 | Non-colour theme character |

**Everything else is derived in CSS with `color-mix()`.** For example:

```css
--app-surface:      color-mix(in srgb, color-mix(in srgb, var(--color-shell-950), white 4%) 92%, transparent);
--app-text-muted:   var(--color-shell-400);
--app-accent-soft:  color-mix(in srgb, var(--color-brand-400) 16%, transparent);
--app-pitch-from:   color-mix(in srgb, var(--app-pitch-light) 24%, transparent);
```

This is deliberate: it keeps the JS payload small, and it means editing one seed moves surfaces, borders and text tones together instead of leaving orphaned greys behind. It also removes any chance of a flash of unstyled colour, since the derivations are in the stylesheet before the first primitive is set.

### Nuxt UI semantic tokens

`--ui-bg`, `--ui-text`, `--ui-border` and friends are re-pointed at the darker end of the shell ramp. Nuxt UI's own `.dark` block maps them to `neutral-900/800/700`, which is too light for this app's depth.

## Themes

Three built-in themes live in `app/utils/theme-definitions.ts` as plain data (`seeds` + `chrome`):

| Theme | Character |
|---|---|
| `premium` (default) | Deep navy shell, emerald accent, gold for silverware. `--ui-radius: 0.5rem`, glass blur, subtle noise. |
| `cyberfoot` | Saturated turf green, amber chrome, `--ui-radius: 0.125rem`, 2px borders, no blur, heavy mown stripes. |
| `classic` | The original emerald/slate palette, preserved. |

The player can override any of the eight seeds from `/game/settings`. Preferences persist to `localStorage` under `fpt:settings:v1`.

### No flash of the wrong theme

`buildPrePaintScript()` in `theme-definitions.ts` generates a dependency-free snippet that `nuxt.config.ts` inlines into `<head>`. It reads localStorage and writes the palette onto `<html>` **synchronously, before the first paint**. The file is kept free of imports (no `colord`) precisely so the config can import it; the colour maths is re-implemented in a few lines rather than pulling a library into the critical path.

Declared in `@theme static`, each becoming an `animate-*` utility:

| Token | Usage |
|---|---|
| `--animate-fade-in-up` | Page section entry |
| `--animate-rise` | Hero/landing entry |
| `--animate-slide-in-left` / `-right` | Feed items |
| `--animate-live-ping` | Pulsing LIVE dot |
| `--animate-shimmer` | Loading skeletons (`.app-skeleton`) |
| `--animate-pop-in` | Player markers, staged substitutions, timeline markers |
| `--animate-scale-in` | Modal entrances |
| `--animate-score-flip` | Score digits on a goal |
| `--animate-glow-pulse` | Drop targets, critical stamina, hero icon |
| `--animate-shake` | Rejected drop / illegal substitution |
| `--animate-flash` | Goal overlay |
| `--animate-sweep` | Route progress bar, live match sheen |
| `--animate-heartbeat` | Injury pause icon |
| `--animate-ticker` | Reserved |

### Motion preferences

Two independent switches, either of which is enough to stop animation:

```css
@media (prefers-reduced-motion: reduce) { /* OS setting */ }
:root[data-motion="reduced"] { /* Settings page */ }
:root[data-motion="off"]     { /* Settings page */ }
```

`data-motion` is set by the settings store and by the pre-paint script.

## Usage patterns

**Prefer the component classes over raw utility chains:**
```html
<!-- ✅ -->
<div class="app-surface">…</div>
```

**Use `style` for one-off token values:**
```html
<span style="color: var(--app-text-muted)">…</span>
```

**Never hardcode a hex in a template.** Every colour should trace back to a token, or the theme editor cannot reach it.
